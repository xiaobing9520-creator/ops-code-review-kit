# Release Notes — v1.7

**Release Date**: 2026-06-01

## Summary

v1.7 solves the **non-deterministic output** problem in `@codebase-reverse-engineering`.
Previously, the same codebase scanned multiple times could produce different architecture
reports (different section ordering, different findings, different file coverage). v1.7
guarantees: **same code + same skill + same model = same architecture output**.

---

## Problem Statement

Users reported that running `@codebase-reverse-engineering` on identical code with
the same model produced inconsistent outputs across runs:
- Tables listed components in different orders
- "Key findings" varied between runs
- Different files were selected for "deep reads"
- Subjective assessments ("well-structured", "notable") changed wording

This made it impossible to diff reports or track changes between code versions.

---

## Root Causes Identified

| # | Root Cause | Fix Applied |
|---|-----------|-------------|
| 1 | Undefined file traversal order (glob/readdir is non-deterministic) | Rule D1: All discovery uses `find | sort`; all listings alphabetically sorted |
| 2 | Subjective "read selectively" instruction with no criteria | Rule D2: Fixed priority chain with explicit scale-based inclusion rules |
| 3 | "Adapt depth" had no hard rules for what to include/exclude | Step 0.1: Deterministic scale thresholds with exact scope definitions |
| 4 | Open-ended template fields encouraged variable-length descriptions | Rule D6: Fixed template completion rules; no extra sections allowed |
| 5 | Tables had no canonical sort key | Rule D4: Every table type has a defined sort key (always alphabetical) |
| 6 | "Key Findings" and "Observations" were inherently subjective | Rule D5: Eliminated all subjective sections; replaced with factual tables |
| 7 | No exclusion rules for transient/generated content | Rule D3: Explicit include/exclude boundaries |

---

## Changes

### 1. Added Determinism Rules (D1–D7)

Seven explicit rules that constrain ALL output to be reproducible:

- **D1** — Canonical File Discovery Order (always sorted)
- **D2** — Deterministic Read Order (fixed priority chain)
- **D3** — Explicit Scope Boundaries (include/exclude lists)
- **D4** — Deterministic Table Ordering (defined sort keys)
- **D5** — Factual Content Only (no subjective assessments)
- **D6** — Fixed Template Completion Rules (no extra sections, exact labels)
- **D7** — No Context Leakage (each run independent)

### 2. Replaced Step 0 ("Scale Assessment & Exploration Strategy")

**Before**: Vague instructions to "adapt depth" and "read selectively"

**After**: 
- Deterministic file count command to classify scale
- Exact scope rules per scale level (Small: read all; Medium: all API + 1st file per package; Large: entry points + 3 files per package)
- Required file manifest generation before analysis
- Fixed module discovery priority chain with mandatory alphabetical sorting

### 3. Replaced Step 1 ("Multi-Package Discovery")

**Before**: Open-ended exploration with "discover ALL packages" and no order

**After**: Step 1 is now "Structured Discovery" with 6 sub-steps executed in
EXACT fixed sequence, each with explicit search patterns and sorted results

### 4. Eliminated Subjective Sections

**Removed**:
- "Key Findings" (was "most important" — subjective ranking)
- "Initial Observations" (was open-ended commentary)
- "Recommended Review Focus Areas" (was subjective prioritization)
- "Documentation Status — quality assessment" (was subjective)
- "Inline Comments: Adequate / Sparse / Excessive" (was subjective)

**Replaced with**:
- "Codebase Facts" table (objective metrics)
- "Review Scope Indicators" table (Yes/No with file path evidence)
- "Modules for Scan" table (deterministic list for @batch-scan)

### 5. All Templates Restructured

Every output artifact template now:
- Has explicit sort key annotations on every table
- Uses only factual fields (counts, paths, versions, names)
- Includes `**Generated by**: @codebase-reverse-engineering v1.7` header
- Prohibits adding sections beyond what the template defines

### 6. Architecture Diagram HTML Preview (New Artifact)

A new file `architecture-preview.html` is generated alongside `architecture.md`.
It renders Mermaid diagrams as visual graphics in any browser — no tooling
installation required.

**Workflow for Word export**:
1. Open `architecture-preview.html` in a browser (Chrome, Edge, Firefox)
2. Mermaid.js (loaded from CDN) renders diagrams as SVG
3. Ctrl+A → Copy → Paste into Word — diagrams embed as images
4. Or: Print → Save as PDF

**Design decisions**:
- Zero dependencies on the review machine (no Node.js, no Puppeteer, no Chrome headless)
- Works on Windows Server with any browser (Edge pre-installed)
- Self-contained HTML with inline CSS; only external dependency is mermaid.js CDN
- Offline fallback: download `mermaid.min.js` and reference locally
- Mermaid source code in HTML is identical to `architecture.md` (single source of truth)

**New output artifact**:
```
code-review-artifacts/reverse-engineering/
├── architecture.md               ← Mermaid source (canonical, diffable)
├── architecture-preview.html     ← Browser-renderable (for Word export)
└── ...
```

### 7. Added Step 8: Self-Validation Checklist

A mandatory pre-save verification that the output conforms to all D-rules.

### 8. Updated Completion Message

Now includes version tag, module count, and HTML diagram usage instructions.

## Impact on Downstream Skills

No changes required to downstream skills (`@batch-scan`, `@sonarqube-review`,
`@secure-coding-baseline-review`, `@summary-report`, `@rescan`). The output
artifact filenames and directory structure remain identical.

The `analysis-summary.md` file now includes a "Modules for Scan" table that
`@batch-scan` can use directly instead of re-discovering modules.

The new `architecture-preview.html` is a deliverable artifact — it should be
included alongside scan reports when delivering results to stakeholders.

## Migration from v1.6

Replace the skill file:

```bash
# The only file changed is the reverse engineering skill
cp ops-code-review-kit/.kiro/skills/codebase-reverse-engineering/skill.md \
   /path/to/target-project/.kiro/skills/codebase-reverse-engineering/skill.md
```

Or replace the entire `.kiro/` directory:

```bash
rm -rf /path/to/target-project/.kiro
cp -r ops-code-review-kit/.kiro /path/to/target-project/
```

**Note**: After upgrading, re-run `@codebase-reverse-engineering` to regenerate
artifacts in the new deterministic format. Previous artifacts will be overwritten.

---

## Verification

To verify determinism, run `@codebase-reverse-engineering` twice on the same
codebase and diff the outputs:

```bash
diff -r code-review-artifacts/reverse-engineering-run1/ \
        code-review-artifacts/reverse-engineering-run2/
```

Expected result: no differences (empty diff output).
